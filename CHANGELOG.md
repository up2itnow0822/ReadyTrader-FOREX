## Changelog

This project follows a lightweight changelog format. Major changes are summarized here to help operators and integrators understand what changed between versions.

### Unreleased

#### Release UAT (every item was found by running the product, fixed, and retested; see `uat/`)
- **The server starts**: `python app/main.py`, the command the README and MCP clients use, failed on imports, and `mcp` 2.x (which drops a module FastMCP imports) was installed by default. The `mcp` SDK is pinned below 2 and both servers run as files. CI now runs ruff, pytest and bandit on Python 3.12 and builds the dashboard.
- **A real paper FX account**: paper orders went to a crypto-style ledger that could not hold a short, valued pairs in the wrong currency and filled at caller-supplied prices. `core/fx_account.py` keeps USD cash and one netted position per pair, charges margin at `LEVERAGE` (30), converts quote-currency P&L to USD, persists in `data/paper.db` and is shared with the API. New `get_paper_account`; `deposit_paper_funds` takes positive USD only.
- **Orders are sized by USD notional against the real account**: the 5% rule valued 4,000 USDJPY as $600,000 and used a fixed $100,000 account. It now uses the order's USD notional against paper (or brokerage) equity, and a BUY it cannot value or size is refused.
- **Paper fills tell the truth**: market orders fill at the latest rate, a limit only when marketable (`limit_not_marketable`), beyond-margin orders are `insufficient_margin`, and malformed orders (side, amount, order type, a limit with no price, a non-pair in paper mode) are refused before anything runs.
- **Live orders obey the switches and the policy on every path**: `LIVE_TRADING_ENABLED` and `TRADING_HALTED` were never read. Every live order, proposal and approval now checks both and the live policy (`ALLOW_EXCHANGES`, `ALLOW_BROKERAGE_SYMBOLS` in any spelling of the pair, `MAX_BROKERAGE_ORDER_AMOUNT`, which refuses live orders when unreadable). `PAPER_MODE` stays on unless explicitly off; `EXECUTION_APPROVAL_MODE` fails closed.
- **No simulated live fills**: an in-memory simulator was still registered as a live venue (`exchange="forex_paper"`) and answered live orders with `status: filled` although nothing reached a broker. It moved to `_deprecated/`; an unknown venue is `brokerage_not_supported`.
- **Brokerage sandboxes by default**: Alpaca live orders go to the Alpaca paper account unless `ALPACA_PAPER=false`; `TRADIER_SANDBOX` and `ETRADE_SANDBOX` accept 1/yes/on and E*TRADE balances follow the sandbox too. OANDA stays on its practice API unless `OANDA_ENVIRONMENT=live`.
- **Approvals work across processes**: proposals are shared through `EXECUTION_DB_PATH` + `EXECUTION_SESSION_ID`, cancelling needs the `confirm_token`, the API answers only the dashboard's origin (`API_CORS_ORIGINS`), and errors say which problem it is (404 unknown, 403 wrong token, 409 refused).
- **An unread calendar is never "no events"**: `get_economic_calendar` read a feed that had moved and reported "No High Impact Events" on every failure. It now reads the ForexFactory mirror (cached 15 minutes, a stale read served with its time), lists the week's high-impact events in UTC, and answers `source_unavailable` when it cannot. News, sentiment and social tools answer `not_configured` / `source_unavailable` instead of error text as news; feeds have timeouts; `fetch_custom_feed` refuses local and private addresses.
- **Research tools**: `run_synthetic_stress_test` (documented, but not an MCP tool) is registered; a failed backtest is `backtest_error`; insights are validated; `get_stock_price` returns a number; `get_multiple_prices` answers null with a reason instead of the string "Error".
- **The dashboard shows the real account**: it displayed fixed made-up figures and linked to pages that do not exist. It now shows the paper FX account from `/api/portfolio`, the mode from `/api/health`, and approving asks for the proposal's `confirm_token`.
- **Setup and demos**: `env.example` lists what the server reads with safe values (it set `API_HOST=0.0.0.0`); the setup wizard checks the FX sources and no longer crashes without a terminal; `examples/paper_quick_demo.py` exercised the crypto engine and failed its own step, and now walks the FX account with self-checks; a malformed optional setting no longer stops the server.
- **Docs match the product**: README, RUNBOOK, ERRORS, EXCHANGES, MARKETDATA, CUSTODY, THREAT_MODEL, POSITIONING and the prompt pack described crypto tools, signers and exchanges; they were rewritten against the running server. `docs/TOOLS.md` is generated from the server's registry (it listed 18 of 29 tools) and a test keeps it current. `smithery.yaml` advertised DeFi integrations; `docker build` no longer copies `.venv`, `.git`, `node_modules` or the local account into the image, and the client configs keep the account in a volume. A crypto signing compose file moved to `_deprecated/`.

#### Cross-repository review (defect classes found in ReadyTrader-Crypto, checked here; `uat/` XR-01..XR-14)
- **Breaking: live approvals need an operator token.** A proposal's `confirm_token` goes to the agent, so an agent that can make HTTP requests could approve its own live order. Set `API_OPERATOR_TOKEN` on the API server: every `/api/` call but `/api/health` then needs `Authorization: Bearer <it>` (the dashboard asks once per tab), and a live proposal is approved only when it is set (`403 operator_token_required` otherwise).
- **Breaking: live OANDA limit orders are fill-or-kill.** A limit went out `GTC` and could rest at OANDA, where later fills escaped the Risk Guardian (which sizes against current positions: five resting SELL limits could turn a long into a large short) and the kill switch. A limit is now a market order with a `priceBound`: it fills now at that price or better, or not at all. Orders use `positionFill: REDUCE_FIRST`, netting as the Guardian sizes them.
- **Every spelling of a pair gets the market checks**: `EUR_USD` and `eur-usd` skipped the volatility halt and the Falling Knife check (the bar lookup read only some spellings). Symbols are normalised to `EURUSD` before any check.
- **Orders are valued at the market**: at a non-FX brokerage an order was sized at the price it carried (a market BUY of 10,000 AAPL with `price=0.0001` was $1). Every order is now valued at the market price (a limit at the higher of its limit and the market); without one, an order that adds exposure is refused. A market order's price is dropped, so a NaN can no longer reach a proposal (it made `/api/pending-approvals` answer 500).
- **Loss limits measure trading results**: a deposit ended a drawdown halt (the drawdown was divided by the capital now in the account), a small loss after a large top-up read as -99% today, and a week-old snapshot was taken as the start of today. The paper account now chains results into a time-weighted index: deposits are neither gains nor losses, the daily baseline is the previous day's last snapshot or the day's first (recorded at the first check of the day), and an account with a position that cannot be priced refuses new exposure instead of reading as unchanged. The daily-loss and drawdown limits run on the paper account only; live orders now list them under `inactive_rules`, and the docs say so.
- **Odd numbers are refused**: deposits over 1e12 USD (two of 1.7e308 made equity infinite), boolean amounts, and non-finite `sentiment_score` values (NaN read as +1.0).
- **The API**: each response carries `X-Request-ID` and security headers, log lines carry their own time and request id, and an internal error answers a JSON 500 naming only the request id (a brokerage refusal of an approved live order answers 502 with its reason).
- **The image**: `.dockerignore` keeps `.env*`, key and database files out in any folder (it matched only a root `.env`) and leaves out the dashboard; the container runs as an unprivileged user.
- **Smithery** no longer offers `EXECUTION_APPROVAL_MODE`: a Smithery launch has no approval API, so every order became a proposal that could only expire. Only the listed settings are passed.
- **The kill switch is documented as it works**: it refuses closing orders too; flatten on the OANDA platform.
- **Breaking for existing Docker volumes: the image runs as an unprivileged user** (`readytrader`, uid 10001). A volume written by an earlier (root) image must be handed over once: `docker run --rm --user 0 -v readytrader-forex-data:/app/data --entrypoint chown readytrader-forex -R 10001:10001 /app/data` (RUNBOOK, "Upgrading a Docker data volume").
- **Independent review of the fixes above** (`uat/` AR-01..AR-10): the operator-token check read the URL's path, so a `Host: 127.0.0.1:8000#` header (or a `--root-path` prefix) let a request past it and an agent approve its own live proposal; it is now a dependency of every protected route. CORS now wraps every answer (a 401 carried no CORS headers, so the dashboard could never ask for the token). A NaN quote passed the size rule and put NaN in the JSON; quotes must be finite and positive. A deposit while a position cannot be priced is refused (it went unrecorded and was later measured as a gain, ending a drawdown halt). Orders the switches refuse are audited again, an approval while halted answers `trading_halted` before the brokerage is called, and `true` is refused for every numeric tool parameter (`limit`, `confidence`, `ttl_seconds` took it as 1).
- **The switches answer first**: with `LIVE_TRADING_ENABLED` off or `TRADING_HALTED` set, a live order is refused as such even when the brokerage is not configured (it answered `brokerage_not_configured`). An order refused because the brokerage account cannot be read now says why (the brokerage's own reason).

#### Earlier in this release
- **Volatility halt and Falling Knife now read prices (security-relevant)**: every trade check and order reads the pair's last 40 daily bars (cached, one fetch per pair per minute). A BUY is refused while the pair is down 5%+ from its highest close of the last four days and still at its lowest close; every trade on the pair is halted while today's move is more than 4.5x its 20-day norm. On 24 pairs the rules had never seen (2000-2026, both directions), a buy on Falling Knife days fell a further 3% within ten days 41% of the time against 12% on all days, and a halt day was followed by a 3% move within five days 15% of the time against 6%. The halt caught the SNB floor removal, Brexit, the 2016 and 2019 flash crashes and the 2018 lira crash. Method, results and caveats: `docs/FALLING_KNIFE.md`; reproduction scripts: `research/falling_knife/`.
- **`get_volatility_status` is implemented**: it returned a hardcoded 1.0, so the halt could never fire; it now returns the measured ratio, or `None` when it cannot be computed. The volatility halt is no longer listed in `inactive_rules` (the news guard still is).
- **The order path now passes the volatility score and news window** to the Risk Guardian; before, neither reached a real order.
- **Missing market data is explicit**: if the bars cannot be read, a BUY is blocked in live mode and allowed-but-flagged in paper mode (`MARKET_GUARD_ON_DATA_ERROR=block|allow` overrides; an unknown value blocks). A SELL is never blocked for missing data. `MARKET_GUARD_ENABLED=false` turns both rules off and lists them in `inactive_rules`.
- **A missing bar for today's session counts as stale**: Yahoo's FX daily bars are London days, Monday to Friday. Once today's London day has started, the provider must have today's bar, or both rules would read yesterday's closes and miss a move happening now. A missing bar blocks a live BUY under the default policy; a SELL is still never blocked for missing data, and without today's move the halt cannot fire.
- **Approvals are rechecked**: with `EXECUTION_APPROVAL_MODE=approve_each`, `/api/approve-trade` re-runs the Risk Guardian with fresh bars before it executes, because a proposal can wait until it expires while the market moves. A refused approval (a Falling Knife BUY, or either side during a volatility halt) answers `409 risk_blocked` and executes nothing.
- **`MARKET_GUARD_ENABLED` fails closed**: only `false`, `0`, `no` or `off` turns the rules off; a typo such as `treu` used to disable them silently.
- **`CIRCUIT_BREAKER_PCT` is documented as unused**: no check ever read it.
- **`docs/TOOLS.md` regenerated** to match the tool signatures.
- **Tests**: 78 new tests (the four that pinned the volatility stub now pin the implementation), including real-bar fixtures (the SNB day from both legs, the 2021 lira collapse, the 2016 GBP flash crash) whose expectations come from the independent research code.
- **Falling Knife gate repaired (security-relevant)**: `analyze_social_sentiment` added a flat `+0.2` for each configured source, so the "sentiment score" measured how many API keys were set rather than what anyone was saying. A panicking feed and a euphoric feed both scored `+0.4`, and the only reachable values were `0.0`, `0.2` and `0.4`. The rule blocks below `-0.5`, so it could never fire.
- **The order path was a bypass**: every order entry point passed a hardcoded `sentiment_score = 0.0` to the Risk Guardian, and passed neither daily loss nor drawdown. Three risk rules were therefore inert on every real order even though `validate_trade_risk` applied them. They now apply.
- **Nothing fabricates a sentiment number any more**: `get_social_sentiment(symbol)` returns the posts themselves, for the calling agent to read and judge. A deterministic text scorer was built and measured first; `docs/SENTIMENT.md` records what it scored and why it was rejected. On 30 simulated pair searches written blind to its vocabulary it caught **none** of eight currency crashes, and it read a rising quote-convention pair (`USDTRY +10.9%`, the lira collapsing) as bullish.
- **The agent can supply its own reading**: `validate_trade_risk(..., sentiment_score=...)` and every order entry point accept a score on `[-1, +1]`, clamped, and the response records `source` as `agent_supplied` rather than as a measurement.
- **The absence of a measurement is visible**: every verdict carries a `sentiment` block (`score`, `source`, `status`, `posts_available`, `posts_age_seconds`) with a `hint`, so a neutral `0.0` is never mistaken for a measured calm market.
- **Cache keyed by normalised symbol**: `EUR/USD`, `eurusd`, `eur_usd` and `EURUSD=X` reach one entry; a pair is never reduced to a base currency, because `USDJPY` and `JPYUSD` are different instruments. Expiry uses the monotonic clock, so a wall-clock step cannot pin or expire an entry, and expired entries are evicted rather than accumulating.
- **Unimplemented risk rules are now declared instead of hidden**: `get_volatility_status` and `get_news_status` are stubs that always return the permissive value, so the 3x-ATR flash-crash halt and the high-impact-news guard never fire. `validate_trade_risk` and blocked orders now return an `inactive_rules` block naming them, so an `allowed` verdict is never mistaken for a fully checked one. (The volatility halt has since been implemented - see the first entry above; the news guard is still a declared stub.)
- **49 new tests** covering the contract above. No new dependency.

### 0.1.0 (2025-12-29) — the ReadyTrader-Crypto code base this repository started from

- **Agent-first MCP server** for crypto trading workflows (paper mode + optional live execution).
- **Safety governance**: risk disclosure consent gate, kill switch, optional approve-each execution with replay protection.
- **Execution breadth**: CEX via CCXT + DEX swaps (1inch builder) with execution routing (`dex`/`cex`/`hybrid`).
- **Market data quality**: websocket-first public streams (opt-in), MarketDataBus freshness selection, plugin feed interface.
- **Stress lab**: deterministic synthetic stress testing with exportable artifacts + heuristic recommendations.
- **Operator layer**: structured logs with redaction, metrics snapshots, optional Prometheus text export, runbook and error catalog.
- **Custody hardening**: signer abstraction (env/keystore/remote), signing intents, defense-in-depth signer policy wrapper.
